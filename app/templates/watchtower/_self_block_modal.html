{# Self-block guard — the "don't lock yourself out" confirmation. The IP block gate in create_app() is unconditional: it 403s every inbound request from a blocked address ahead of routing, with no exemption for signed-in admins. So banning the IP you're currently browsing from locks you out of the whole portal, and the only way back is editing the database by hand. That's a mistake worth one deliberate extra step. This partial is included by every Watchtower template that renders a Block button (overview, access, requests, 404s). It contributes two things: 1. The modal itself, rooted at the end of the page body. 2. A capture-phase submit listener that intercepts *any* form posting to /watchtower/ban-ip whose `ip` field matches this admin's own address. Capture phase matters: the 404s tab binds its own bubble-phase handler to the same forms to POST them over fetch. Running first (and calling stopPropagation) lets this guard pre-empt that handler, and the "confirm" path re-submits the form so whatever page-specific handler existed still does its normal job. Matching on the form's action rather than a marker class means new Block buttons are covered the day they're added, without having to remember to opt them in. #}
